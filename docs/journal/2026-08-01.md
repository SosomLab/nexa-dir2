## X-37 Connect Cloud — 브라우저 OAuth 직접 연결 (사용자 결정 — 같은 브랜치 6커밋째)

사용자 요청: "Connect Cloud 메뉴 + 하위 OneDrive/Google Drive/Dropbox — 선택하면
**현재 연결된 계정이 아닌 다른 계정**을 브라우저로 추가".

### 사실 확인 → 방식 결정

- 조사: **3사 모두 계정 추가를 CLI로 노출하지 않는다**(GUI 전용, 그 안에서 브라우저가
  열림). 클라이언트 다계정 수도 제한(OneDrive 개인 1개·GDrive 4개).
  → 클라이언트 우회 = **앱이 직접 API 인증**이 유일한 해법.
- 사용자에게 2안 제시(클라이언트 계정 추가 유도 vs OAuth 직접 연결) →
  **OAuth 직접 연결(Phase B 전체) 채택**.
- 중요 제약 고지: 토큰만으로는 탐색 불가 — 진짜 OAuth 방식은 공급자/Provider까지
  포함한 X-37 전체 작업. 이번 슬라이스는 **인증·연결 등록까지**.

### ADR-0006 신설 + DR-2 개정

- PKCE 공용 클라이언트(`client_secret` 미사용·미동봉) · **루프백 리디렉션**
  (커스텀 스킴은 DR-3 레지스트리 비의존과 충돌) · WinHTTP(대안 4종 비교표) ·
  DPAPI 보관 · **client_id 사용자 제공**(Google restricted scope 심사 회피) ·
  플러그인화는 ABI 실측 후로 **순서만** 규정(DR-7 유지).
- **B3 화이트리스트 +4**: `winhttp`·`crypt32`·`ws2_32`·**`bcrypt`**.
  마지막 것은 **게이트 실행으로 발견** — CNG 해시가 기존 `bcryptprimitives`(std RNG)와
  **별개 DLL**을 끌어온다는 사실이 실측으로 드러났다(예산 게이트가 제 역할을 한 사례).

### 구현

| 모듈 | 내용 |
| --- | --- |
| `oauth.rs` | Service 3종(엔드포인트·scope·me_url) · PKCE verifier/challenge(CNG SHA-256) · base64url·percent·최소 JSON **수제 구현**(crate 0) · 루프백 1회 수신(state 대조·브라우저에 안내 페이지 응답) · WinHTTP 토큰 교환/refresh · 핸들 RAII |
| `secret.rs` | refresh 토큰 DPAPI 암호화 → `data\secrets\cloudN.tok`(hex 1줄 — 포터블 진단 용이). 타 PC 이동 시 복호 실패 = 재로그인(**평문 무유출 = 의도된 특성**) |
| `config.rs` | `CloudConn.account`(경로 비움+account = API 연결 — `is_api()`) · `cloud_client_id_<종류>` |
| `win.rs` | Cloud 메뉴 하단 **Connect Cloud** → client_id 확인(미설정 = 등록 절차 안내 모달) → **[브라우저 열기]/[URL 복사]/[취소] 모달**(URL 복사 = 프라이빗 창 다계정 — 사용자 요청) → 워커 대기·교환 → `WM_APP_CLOUD_AUTH`(재시도 통지) → 연결 등록·토큰 저장. 재인증은 행 갱신·해제 시 토큰 폐기 |

### 설계 메모

- **온라인 보기 로그인**: OAuth 토큰으로 브라우저 세션을 로그인시키는 것은 불가
  (쿠키는 브라우저 소관 — 검토서 26 §2). 기본 브라우저 세션이 로그인 상태를 결정하고,
  **URL 복사**가 프라이빗 창 다계정 접속 경로(사용자 확정 대안).
- 추가 명령 인덱스는 **메뉴 구성 시점 후보 스냅숏**(`st.cloud_cands`)으로 해석 —
  표시와 실행 사이 환경 변화로 어긋나지 않게.
- 내 PC 정렬은 드라이브·클라우드 혼합 이름순(α — 섹션 분리 정렬은 후속 검토).
