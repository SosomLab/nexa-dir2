## 릴리스 채널 제출 규칙 명문화 (사용자 지시 — 릴리스마다 반영)

**지시**: winget·choco의 배포 요청 상태를 확인해 **대기 중인 버전이 없으면 릴리스 후
그 버전을 제출**하고, **대기 중인 버전이 있으면 그 채널은 제외**하도록 규칙화하고
릴리스마다 반영할 것.

- 이 판단은 08-02("0.13.0 PR OPEN이라 0.14.0 보류")·08-11("0.15.0을 건너뛰고
  0.16.0으로 한 번만")에서 **건별로 두 번 내린 것과 같은 결론**이라, 개별 판단을
  **상시 규칙으로 승격**한 것. [21 §8 "릴리스 시 채널 제출 규칙"](../21-distribution.md)
  신설 + CLAUDE.md §7 채널 항목에 규칙 링크.
- **채널별 "대기 중" 판정 원천**: winget = 우리가 제출한 PR이 OPEN인가(같은 패키지에
  PR이 겹치면 안 된다 — 병합/닫힘 후 제출) · Chocolatey = 모더레이션 미승인 버전이
  있는가(현재 0.8.1 두 패키지가 07-20 스캔 플래그로 잠김 → **계속 제외** — 기존
  `CHOCO_PUSH` 게이트·사용자 지시와 합치. 승인되면 그 시점 최신 버전부터 재개).
- **제외했다가 재개할 때는 중간 버전을 건너뛰고 최신 버전만** 제출한다(winget은
  중간 버전 생략 무방 — 08-11 확립).
- 세션 메모리에도 등재(`release-channel-submit-rule`) — 릴리스 절차를 밟는 세션이
  규칙을 놓치지 않도록.

## X-42 가상 파일 붙여넣기 — RDP·Outlook·압축 폴더 폴백 (`227ed4c` — main 직커밋, 실기 QA 대기)

**보고**: 맥 → 윈도우 RDP 세션에서 맥 파일을 복사해 붙여넣으면 **탐색기는 되는데
앱에서는 안 된다**. 기능 확인 + 보완 검토 요청 → 검토 후 사용자 승인으로 구현.

### 원인 — RDP 파일 클립보드는 CF_HDROP이 아니다

- 앱 읽기측(clipboard.rs `has_files`/`read_file_list`)이 **CF_HDROP(실경로 목록)
  단일 포맷**이었다(M3-5 규약 — 탐색기↔앱 상호운용에는 충분했다).
- 맥에서 복사한 파일은 **원격 Windows 디스크에 존재하지 않는다** — rdpclip은
  경로 대신 **가상 파일 2종**을 게시한다: `FileGroupDescriptorW`(항목 목록·이름·
  크기·속성) + `FileContents`(항목별 내용 — 붙여넣는 순간 RDP 채널로 지연
  스트리밍). 탐색기는 이 MS 규약(CFSTR_FILEDESCRIPTORW/CFSTR_FILECONTENTS)을
  지원해서 됐고, 우리는 `has_files()` false → 메뉴 비활성/Ctrl+V 무반응.
- **같은 규약을 쓰는 소스가 더 있다**: Outlook 첨부 복사·탐색기 zip 내부 항목·
  MTP 기기(폰) — 전부 이번 폴백으로 함께 열린다. X-38(7-Zip DnD 지연 렌더링)과
  친척이지만 다른 층위다 — 7-Zip은 CF_HDROP을 **늦게** 만들고, RDP는 CF_HDROP을
  **아예 안** 만든다.

### 구현 (1차 슬라이스 — 동기 추출)

- **판정**: `has_files()` = CF_HDROP **또는** FileGroupDescriptorW(신설
  `has_virtual_files()`) — 붙여넣기 메뉴가 가상 파일에도 활성화된다.
  `sync_cut_marks`는 `read_file_list()`가 None을 돌려줘 빈 집합으로 수렴(무해).
- **추출**(`extract_virtual_files` → `extract_virtual_from` 본체 분리):
  `OleGetClipboard()` → `IDataObject`. 원시 `GetClipboardData`로는 안 되는 이유 =
  FileContents는 **lindex(항목 인덱스)** 지정이 필요해 FORMATETC를 받는 OLE
  경로만 가능. 디스크립터(HGLOBAL) 파싱 → 항목별 `GetData(FileContents,
  lindex=i, TYMED_ISTREAM|TYMED_HGLOBAL)` — rdpclip·Outlook은 IStream(64KiB
  루프·크기 미상은 EOF까지), 일부 소스는 HGLOBAL(크기 힌트로 여분 패딩 방어).
- **안전장치**: 디스크립터 이름은 **신뢰 불가 외부 데이터** — `..`·절대 경로·
  드라이브 문자는 항목째 기각(경로 탈출 방지) · cItems가 실제 버퍼보다 커도 담긴
  만큼만(손상 방어) · 항목별 실패 격리(부분 성공 허용 — 전송 엔진 규약 동일) ·
  최상위 이름 충돌은 `nexa_ops::unique_dest` " (2)"(하위 항목은 같은 매핑 추종·
  자식이 부모 디렉터리 항목보다 먼저 와도 성립).
- **배선**(win.rs `paste_virtual`): Ctrl+V·배경 메뉴 paste 동사·고유 붙여넣기·
  pasteInto 4개소 — **CF_HDROP이 있으면 기존 전송 엔진(undo 포함)이 우선**,
  없을 때만 폴백. 클라우드 대상은 무동작(로컬 FS 기록 불가 — 업로드 연계는 후속).
  완료 시 양쪽 재로드.
- **함정(빌드에서 발견)**: `FILEDESCRIPTORW`는 **packed 구조체** — 배열 필드
  참조가 E0793(정렬 UB). 값 복사(`let buf = fd.cFileName`)로 우회.

### 검증

- **테스트 2건 신설**(총 110 green): ① 디스크립터 파싱 — 한글 이름·하위 경로·
  크기 미상·탈출 2종 기각·cItems 과대 방어 ② **종단** — `#[implement(IDataObject)]`
  가짜 소스(rdpclip 형상: 디스크립터 HGLOBAL + SHCreateMemStream)로 실 클립보드
  비접촉 추출: 파일 내용·하위 폴더·64KiB 초과(100KB) 스트림·기존 파일 무손상·
  " (2)" 충돌까지. `extract_virtual_from` 분리가 이 테스트를 가능하게 했고,
  후속 DnD 수신 재사용 지점이기도 하다.
- clippy `-D warnings` 0 · 비Windows check 통과(warning 14건은 svg 모듈 기존
  dead-code — 변경분은 전부 `#[cfg(windows)]` 안) · **B2 3.67MB**(release 실측
  3,667,456 B) · **B3 통과 — 신규 DLL 0**(OleGetClipboard는 ole32 — M3-5부터 사용).
- **실기 QA = 사용자 몫**(맥 RDP 환경 필요): 맥 Finder 복사 → 앱 붙여넣기(단일·
  다중·폴더·대용량·한글 이름). Outlook 첨부·zip 내부 항목 붙여넣기도 같은 경로.
