**커밋 대기분이 없다.** 그래서 정리 대상은 코드가 아니라 **문서 자체의 어긋남**이고,

### ① STATUS "한 장" 규약 재이탈 — 565 → 161줄

07-24에 382→175줄로 압축했던 문서가 차수 25건·**565줄**로 되돌아갔다. 규약([16 §1](../16-doc-git-conventions.md))의
STATUS는 "지금 상태 한 장"이고 상세는 journal이 원본이므로, **08-02 2건만 원문 유지**하고
**08-01 이전은 하루 한 줄 색인**으로 압축했다(각 줄에 journal 링크 — 원문은 삭제되지 않는다).

재발이 반복되는 이유는 분명하다. 한 작업을 마칠 때 STATUS 맨 위에 원문을 쌓는 것은 규약이지만,
**쌓기만 하고 아래를 접는 사람이 없다.** 압축은 하루가 끝날 때가 아니라 **정리 요청이 올 때** 하는
현재 방식이 유지되는 한 주기적으로 다시 부풀 것이고, 그건 감수 가능한 비용으로 본다(원문 손실이 없으므로).

- 자산 **5종 첫 실배포 확인** — 07-31에 추가한 zip 2종 + `SHA256SUMS.txt`가
  실제 태그에서 정상 생성됐다(그때는 dry-run만 했다).
  포터블 exe 3.43MB · zip 1.54MB · 설치형 exe 3.09MB · zip 2.57MB.

  nupkg 팩 자체는 돌지만 커뮤니티 저장소로 나가지 않는다.

### winget Portable 0.13.0 — [#410978](https://github.com/microsoft/winget-pkgs/pull/410978)

`packaging/winget/portable/0.13.0/` 3파일 생성(0.12.0 복사 → 버전·URL·SHA·날짜 교체).
SHA-256은 릴리스가 발행한 `SHA256SUMS.txt`와 **대조 확인**(재계산이 아니라 원천 대조).
`Description` 하이라이트에 클라우드 항목 추가 — 0.13.0의 핵심 기능이라 스토어 문구가
기능을 반영해야 한다. 제출은 `kiros33` 계정(포크 소유자)으로, 끝난 뒤 원래 계정 원복.

### 발견: main CI가 비Windows에서 깨져 있었다 (2연속)

버전 승격 push 후 확인하다 발견. **Windows 잡은 통과**했고 릴리스 산출물도 무사했으나,
`core`(ubuntu·macos) 잡이 실패 중이었다 — 클라우드 작업이 들여온 회귀다.

- **1차** `cannot find win/dialog in crate` — `cloudfs`가 전 플랫폼 컴파일 대상인데
  `crate::win`(통지·`plock`)·`crate::dialog`(진행 창 세그먼트)를 **43곳** 참조한다.
  순수 로직 모듈이 아니라 UI와 맞물린 워커이고 **소비자도 `win.rs` 하나뿐**이라,
  `ctl`·`watcher`·`dnd`와 같은 `#[cfg(windows)]`로 맞췄다(`3b2b0b5`).
- **2차** 첫 오류를 걷어내자 드러난 `E0282` — `cloud::detect()`의 `Vec::new()`가
  비Windows에서 원소 타입을 추론할 근거를 잃는다(cfg 블록 안의 `detect_*(&mut out)`
  호출이 통째로 사라지므로). 타입 명시로 해결. `Path`도 `detect_googledrive`
  전용이라 미사용 경고 → cfg 게이팅(`21a97c3`).

- **3차 — 실은 07-27부터 붉었다**: 컴파일 오류를 걷어내자 그 아래 **테스트 실패
  2건**이 드러났다. CI 이력을 뒤져 보니 main의 `core` 잡은 **최소 07-27부터 연속
  실패** 중이었다 — 클라우드 작업이 만든 것이 아니라 **원래 깨져 있던 것**이고,
  Windows 잡만 통과해 일주일 넘게 눈에 띄지 않았다("main 항상 green" [15](../15-dev-methodology.md)가
  그동안 깨져 있었다는 뜻이다).
  - `open_any_root_finds_a_root`(07-31 S6와 함께 추가): 후보가 `C:\`·드라이브
    문자·`%USERPROFILE%`뿐이라 비Windows에서는 항상 `None` → `#[cfg(windows)]`.
  - `sample_wasm_plugin_end_to_end`: Mermaid flowchart는 **3단 폴백**
    (이미지 마커 → 아트 → **원문 모노 블록**)인데 단언이 앞의 둘만 인정했다.
    호스트 `render_svg`가 없는 환경에서는 원문 보존으로 떨어지며 이 역시 계약대로다
    → 단언 확장(`64dc123`). **3잡 전부 green 복귀 확인**.

**절차 보완**([18 §2·§4](../18-build-and-test.md)): 두 번 연속 같은 사각지대에
빠진 것이 문제다. Windows에서 `cargo test`가 green이어도 **cfg 블록이 사라지는
비Windows 경로는 전혀 검증되지 않는다**. 로컬에서 같은 경로를 재현하는
`cargo check --workspace --all-targets --target x86_64-unknown-linux-gnu`를
명령 목록에 넣고, core 잡이 사각지대라는 경고를 §4에 명시했다. 링커가 필요 없어
`cargo check`로 충분하며, 이번 2차 수정은 실제로 이 명령으로 검증했다.

## 클라우드 사용자 매뉴얼 신설 + 콘솔 브랜딩 자산 (사용자 요청 — `0eb183d`)

사용자 요청: "사용자별 정보를 넣어 쓸 수 있게 설정 항목이 추가됐다니 **위키·사용자
설명서에 꼭 들어가도록** 항목 추가와 상세 가이드를 넣어 달라."

착수하며 확인한 사실: **위키에 클라우드 문서가 아예 없었다.** X-36(링크)·X-37(직접
연결) 전체가 매뉴얼에 미기재 상태였다 — 요청한 설정 항목만 끼워 넣으면 문맥 없는
파편이 되므로 **기능 전체를 매뉴얼화**했다.

### 새 페이지 `기능-클라우드.md` (222줄)

- **Link vs Connect 구분표를 맨 앞에** — 둘을 섞으면 나머지가 전부 헷갈린다.
  (링크 = 이미 설치된 동기화 폴더를 내 PC에 얹기 / 직접 연결 = 앱이 API에 로그인)
- 연결 절차·다른 계정 로그인(프라이빗 창 URL 붙여넣기)·가능한 작업 목록.
- **토큰 보관**: DPAPI = 사용자+PC 바인딩 → 포터블 폴더를 옮기면 재로그인.
  "불편"이 아니라 **의도된 안전장치**임을 명시(USB 분실 시 토큰 미유출).
- **서비스별 발급 절차 3종** — 각각 실제로 걸려 넘어졌던 함정을 그대로 적었다:
  - OneDrive: **퍼블릭 클라이언트**여야 함(웹으로 등록하면 시크릿을 요구해 실패)·
    **시크릿 만들지 말 것**·`127.0.0.1`은 포털이 등록 거부 → `localhost`
  - Google: **데스크톱 앱에도 시크릿 필수**(빠지면 마지막 단계에서 조용히 실패)·
    `drive.file`은 앱 생성 파일만 보여 **탐색기로 무용** → `drive`
  - Dropbox: **Full Dropbox**(App folder는 사후 변경 불가)·리디렉션 **3개 정확 일치**
- 한도표(누가 쓸 수 있나)·문제 해결표 8행.

### `기능-설정.md` — "파일 직접 편집" 절 신설

설정 창에 없는 고급 항목을 다루는 자리를 처음 만들었다. `cloud_client_id_*`·
`cloud_client_secret_*` 키 표 + **서비스별 시크릿 필요 여부**(OneDrive는 넣으면 안 됨)
+ **변경 후 재연결 필수**(옛 ID로 받은 토큰은 새 ID에서 무효). 영속 위치에
`data\secrets\` 추가. 색인 3곳 배선(_Sidebar·Home·기능-개요).

### 앱 안내 문구의 **잘못된 리디렉션 URI** 정정 (lang 3종)

문서를 쓰며 대조하다 발견 — `cloud.err.noClientIdMsg`가 리디렉션 URI를
**`http://127.0.0.1` (루프백·포트 임의)** 라고 안내하고 있었다. 실제 구현은
`localhost` **고정 포트**(Dropbox는 53682~53684 정확 일치)다. **안내대로 따르면
등록이 실패한다.** 시크릿 안내도 없어 Google·Dropbox는 발급해도 로그인이 안 되는
문구였다. 서비스별 URI + 시크릿 키 + 위키 참조로 교체.

기능 구현 뒤 **사문(死文)이 된 키 2개 제거** — `cloud.readonly`("현재 읽기 전용")·
`cloud.err.crossAccount`("계정 간 복사 미지원")는 둘 다 **사실과 반대**가 됐고
참조도 없었다.

## 3사 배포 인원 한도 점검 (사용자 질의 — `3e13876`)

사용자 질의: "OneDrive·Dropbox는 Nexa Dir 사용자들이 쓸 수 있어 보이는데 전체 점검해
달라." → **셋 다 무제한이 아니고, 벽의 종류가 서로 다르다**는 결론.

| 서비스 | 지금 쓸 수 있는 사람 | 벽 | 해제 조건 |
| --- | --- | --- | --- |
| Dropbox | **누구나**(500명까지) | 50명에서 **2주 카운트다운** | 프로덕션 승인(무료·수일) |
| OneDrive | **개인 MS 계정 = 무제한** | **조직 계정은 동의 불가** | 게시자 확인(CPP + 도메인 DNS) |
| Google Drive | 테스트 사용자 100명 | 프로덕션 게시해도 **100명 유지** | CASA Tier 2(수개월·유료) |

**기존 ADR 서술 2건을 정정**했다.

- OneDrive "게시자 인증(**선택**)" → **틀렸다**. 2020-11-08 이후 등록된 멀티테넌트
  앱은 "기본 로그인+프로필 읽기"를 넘는 권한에 **테넌트 밖 사용자가 동의 불가**하며,
  우리 `Files.ReadWrite`가 정확히 그 대상이다. 개인 MS 계정은 테넌트 밖이 아니라
  무관 — 08-01 QA에서 `sybae76@outlook.com` 연결이 정상 동작한 것이 방증.
  표의 scope 표기도 현행(`Files.ReadWrite`)으로 정정.
- Google "미인증 = 100명·경고"에 더해, **프로덕션 게시로도 상한이 유지**되고 그
  100명은 **프로젝트 수명 누적·리셋 불가**임을 명시. scope 표기도 `drive`로 정정.

**함의**: 조직 계정 사용자는 **동기화 폴더 Link로 우회 가능**하다 — Connect만 막힐 뿐
기능 전체가 막히는 것이 아니다. 이 점을 ADR-0006 §2-4-1로 신설해 기록.

## 3사 앱 등록 완료 — 잔여를 "배포 선행 조건"으로 재분류 (사용자 확인 — `07b617a`)

사용자가 Dropbox·Google·Entra 콘솔 등록을 마치고 화면을 공유. 코드의
`default_client_id` 3종과 모두 일치 확인. Entra 앱은 **All Microsoft account
users·퍼블릭 클라이언트·시크릿 없음**으로, 우리 PKCE 흐름과 정확히 맞는 구성이다
(개인 계정이 아닌 **테넌트에 등록**된 점도 다행 — 개인 계정 등록 앱은 게시자 확인
자체가 불가해 재등록이 필요했을 것).
