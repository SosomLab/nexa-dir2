# ADR-0006 — 클라우드 직접 연결(OAuth2 PKCE) · B3 화이트리스트 확장

- **상태**: 채택(2026-08-01 — 사용자 결정: "OAuth 직접 연결 = Phase B 전체")
- **맥락**: [26 검토서](26-cloud-integration-study.md) §3 · X-37
- **개정 대상**: **DR-2**(B3 임포트 = OS 인박스만 — 목록에 `winhttp.dll` 추가) ·
  DR-8(외부 crate 0 유지 — 본 결정은 crate 추가 **없음**)

## 1. 배경

X-36(08-01)으로 **이미 동기화된** 클라우드 폴더를 This PC에 연결하는 경로는 완성됐다.
그러나 사용자 요구는 "**동기화 클라이언트에 연결된 계정이 아닌 다른 계정을 브라우저로
추가**"다. 조사 결과 세 클라이언트(OneDrive·Google Drive·Dropbox) 모두 계정 추가를
**CLI로 노출하지 않고** GUI 전용이며, 클라이언트가 지원하는 다계정 수에도 제약이 있다
(OneDrive 개인 = 1개). 따라서 클라이언트 우회 = **앱이 직접 클라우드 API에 인증**하는
경로가 유일한 해법이다.

## 2. 결정

### 2-1. 인증 = OAuth2 Authorization Code + **PKCE**(공용 클라이언트)

- 데스크톱 앱은 시크릿을 안전히 보관할 수 없다 → `client_secret` **미사용·미동봉**.
  PKCE(RFC 7636)가 3사 공통 지원되는 표준 대안이다.
- 리디렉션 = **루프백**(`http://127.0.0.1:<임의 포트>/`) — 3사 모두 공식 허용.
  커스텀 스킴(앱 프로토콜 등록)은 **포터블 규율(DR-3: 레지스트리 비의존)과 충돌**하므로
  채택하지 않는다.
- `state` 무작위 대조로 CSRF 차단, 리스너는 **1회 수신 후 즉시 종료**.

### 2-2. 네트워크 = **WinHTTP**(OS 인박스) — B3 화이트리스트 `winhttp.dll` 추가

- 대안 비교:

  | 후보 | 판정 |
  | --- | --- |
  | **WinHTTP**(winhttp.dll) | ✅ 채택 — 인박스·TLS는 schannel 위임·서비스 친화·crate 0 유지 |
  | reqwest/ureq + rustls | ❌ crate 대량 추가(DR-8 위반)·B2 급증 |
  | WinINet | ❌ 사용자 세션/캐시 결합(자동화 부적합·MS 권고 아님) |
  | raw socket + 자체 TLS | ❌ TLS 자체 구현은 보안상 금기 |

- **DR-2 개정**: B3 화이트리스트에 **4개 추가**(전부 OS 인박스 — "인박스만" 원칙 불변):

  | DLL | 근거 |
  | --- | --- |
  | `winhttp.dll` | 토큰 교환·API 호출(TLS = schannel 위임) |
  | `crypt32.dll` | 토큰 DPAPI 보관(`CryptProtectData`) |
  | `ws2_32.dll` | 루프백 리디렉션 1회 수신(127.0.0.1 한정) |
  | `bcrypt.dll` | PKCE `code_challenge` SHA-256(`BCryptHashData`) — 기존 `bcryptprimitives.dll`(std RNG)과 **별개 DLL**임이 실측으로 드러남(게이트가 포착) |

- B1(RSS ≤30MB)·B2(exe ≤10MB)는 **불변** — 게이트로 계속 검증(실측 3.28MB).

### 2-3. 토큰 보관 = **DPAPI**(crypt32, 인박스)

- `CryptProtectData`(사용자+머신 바인딩) → `data\secrets\cloud<N>.tok`.
- **포터블 특기(의도된 동작)**: `data\`를 다른 PC로 옮기면 복호가 실패해 재로그인이
  필요하다. USB에 평문 토큰이 남지 않는 안전 특성이므로 결함이 아니며 안내 문구로 노출.
- refresh 토큰으로 무개입 갱신, 철회·만료 시에만 재로그인 요구.

### 2-4. `client_id` = **하이브리드**(NexaDir 기본값 + 사용자 재정의)

> **개정 08-01**(사용자 지적 "NexaDir 기준으로 발급받아야 하지 않나"): 초판은 전 서비스를
> "사용자 제공"으로 뒀으나, 이는 **Google 제약 하나를 3사 전체에 과적용**한 것이었다.
> 정상 모델은 벤더 1회 등록이며, 서비스별로 요건이 갈린다.

**해석 순서 = 설정 `cloud_client_id_<종류>` > `Service::default_client_id`**
(rclone 등 관례). PKCE 공개 클라이언트라 exe 동봉은 시크릿 유출이 아니다.

| 서비스 | 벤더 등록 | 비용 | 제약 | 현 상태 |
| --- | --- | --- | --- | --- |
| **OneDrive**(Entra) | 권장 | **무료** | 개인 MS 계정은 **인원 제한 없음**. 단 **조직(회사·학교) 계정은 게시자 확인 없이는 동의 차단**(§2-4-1) | ✅ 등록 완료 `6685a1af-…` |
| **Dropbox** | 권장 | **무료** | 개발 상태 최대 500명, **50명 연결 시 2주 내 프로덕션 승인 신청**(심사 무료·수일. 미신청 시 신규 연결 동결) | ✅ 등록 완료 `ofcq452…`(Development) |
| **Google Drive** | 보류 | **연 $500~4,500** | `drive` = restricted scope → **CASA 연간 유료 감사 + 매년 재검증**. **미인증이면 프로덕션으로 게시해도 100명 상한이 유지**되고, 이 100명은 **프로젝트 수명 누적·리셋 불가**. `drive.file`은 감사 면제지만 앱이 만든 파일만 보여 **탐색기로는 무용** | ✅ 등록 완료(테스트 모드 2/100) |

### 2-4-0. 시크릿 동봉 — **유지 확정** (08-02 사용자 결정)

main push가 GitHub Push Protection에 막히면서(공개 저장소 · Google client_id/secret
탐지 · 사용자가 2건 모두 수동 허용) "숨길 방법이 있는가"를 재검토했고,
**현행 유지**로 확정했다. 아래는 그때 확인한 사실 — **다시 검토하지 않기 위해** 남긴다.

- **`client_id`는 애초에 비밀이 아니다.** 인증 시 브라우저 주소창에 그대로 실린다.
  Push Protection이 잡은 것은 Google의 탐지 패턴이 id·secret을 함께 보기 때문이지
  id가 기밀이라서가 아니다. **실제 쟁점은 secret 하나뿐.**
- **OneDrive**: 이미 secret 없음(PKCE 퍼블릭 클라이언트).
- **Dropbox**: PKCE만으로 토큰 교환이 **가능하다** — 기본값을 비우면 제거된다.
  기술적으로 열려 있으나 **사용자 결정으로 유지**한다.
- **Google**: PKCE로 대체 **불가**. refresh 발급에 client_secret을 요구한다
  (RFC 8252 권고와 배치되는 Google 고유 제약). **서버 경유가 유일한 은닉 수단**이며,
  이는 DR-3(포터블·서비스 비의존) 위반 + 사용자 토큰이 우리 서버를 경유하는
  프라이버시 악화라 채택하지 않는다. 난독화는 스캐너·grep 회피일 뿐 보안이 아니다.
- **이미 공개된 값은 되돌릴 수 없다.** 소스에서 빼도 git 히스토리에 남으므로,
  실제 무효화는 콘솔 재발급(rotate)뿐이다. 새 값도 결국 동봉되므로 실익이 없다.
- 편익 대비 노출: 동봉 Google ID는 어차피 **누적 100명**까지만 쓸 수 있다
  (§2-4-1). 그 이상은 사용자별 발급이 필요하며, 경로는 이미 열려 있다.

**결론**: 3사 모두 현행 유지. 방어선은 시크릿 기밀성이 아니라
**리디렉션 URI 화이트리스트 + 사용자 브라우저 로그인 + 세션별 PKCE verifier**다
— 시크릿만으로는 어떤 사용자 데이터에도 접근할 수 없다.

### 2-4-1. 사용자 배포 한도 점검 (08-02 — 사용자 질의 "다른 사람도 쓸 수 있나")

3사 등록을 마친 뒤 **"동봉 ID로 제3자가 실제로 쓸 수 있는가"** 를 원천 확인했다.
결과는 **셋 다 무제한이 아니며, 벽의 종류가 서로 다르다**.

| 서비스 | 지금 쓸 수 있는 사람 | 벽 | 해제 조건 |
| --- | --- | --- | --- |
| **Dropbox** | **누구나**(500명까지) | 50명에서 **2주 카운트다운** 시작 | 프로덕션 승인 신청(무료·수일) |
| **OneDrive** | **개인 MS 계정 = 누구나·무제한** | **조직 계정은 동의 불가** | 게시자 확인(CPP 계정 + **커스텀 도메인 DNS 검증**) |
| **Google Drive** | 테스트 사용자 100명(누적·리셋 불가) | 프로덕션 게시해도 **100명 유지** | CASA Tier 2(수개월·유료) |

**OneDrive 조직 계정 차단의 근거**: 2020-11-08 이후 등록된 멀티테넌트 앱은, **앱이
등록된 테넌트 밖의 사용자**가 "기본 로그인 + 프로필 읽기"를 넘는 권한에 동의할 수 없다
(위험 기반 단계적 동의). 우리는 `Files.ReadWrite`를 요구하므로 **정확히 이 대상**이다.
개인 MS 계정은 테넌트에 속하지 않아 영향이 없다 — 실제로 08-01 QA에서
`sybae76@outlook.com` 연결이 정상 동작했다.

**게시자 확인이 간단하지 않은 이유**: CPP(구 MPN) 계정 + **Entra에서 DNS로 소유를 검증한
커스텀 도메인**이 요구된다. `*.onmicrosoft.com` 기본 도메인으로는 불가하므로,
도메인 보유가 선행 조건이다. 앱이 개인 계정이 아닌 **테넌트에 등록돼 있는 점은 다행**
(개인 계정 등록 앱은 게시자 확인 자체가 불가라 재등록이 필요했을 것).

**함의**: 조직 계정 사용자는 **동기화 폴더 Link**(X-36 — OAuth 불요)로 우회할 수 있다.
Connect(직접 연결)가 막힐 뿐 기능 전체가 막히는 것은 아니다.

**포터블 특유 위험(하이브리드 채택 근거)**: 동봉 ID는 **전 사용자가 쿼터를 공유**하므로
레이트 리밋을 함께 맞고, 악용 시 앱 등록 자체가 정지되어 전원이 끊긴다. 따라서 기본값을
제공하되 **사용자 재정의 경로를 항상 열어 둔다**(대량 사용자·조직은 자기 ID 권장).

구현: [`oauth::Service::default_client_id`](../crates/nexa-app/src/oauth.rs) 상수 —
등록 완료 시 **이 값만 채우면** 재배포로 전 사용자에게 적용된다.

### 2-5. 플러그인화는 **후속** — 1차는 호스트 내장

- 검토서 §3-2는 공급자를 `kind: cloud` WASM 플러그인으로 뒀으나, **1차는 호스트에
  직접 구현**한다. 근거: ABI를 먼저 고정하면 실사용 전 추측 설계가 되고, wasmi 호출은
  동기라 네트워크 잡 모델(워커+통지)이 선행 확정돼야 한다.
- 호스트 구현으로 3사를 돌려 **ABI 요구사항을 실측**한 뒤 플러그인 경계를 그린다
  (DR-7 정신 유지 — 이 ADR은 DR-7을 폐기하지 않고 **순서만** 정한다).

## 3. 결과·범위

- **1차 슬라이스(이 ADR 이행 시작)**: 인증 인프라 + `Connect Cloud` 메뉴 —
  브라우저 로그인 → 토큰 획득·DPAPI 저장 → 연결 등록(계정 표시명 포함).
- **2차**: 탐색(읽기) — `::CLOUD:<id>::` 센티널 + 워커 목록 조회·캐시 → 트리 열거.
  UI 스레드 네트워크 호출 **금지**(07-21 SHFileOperation 교훈 계승).
- **3차**: 다운로드/미리보기 → **쓰기**(업로드·삭제·이동 + ETag/rev 충돌 UX).
- 기존 X-36(동기화 폴더 연결)은 **그대로 유지** — 두 방식은 공존하며 연결 목록에서
  종류로 구분한다(`sync` vs `api`).

## 4. 위험·완화

| 위험 | 완화 |
| --- | --- |
| 루프백 포트 충돌·방화벽 프롬프트 | 임의 고포트 바인드·**127.0.0.1 한정**(외부 노출 없음)·실패 시 재시도 |
| 토큰 탈취 | DPAPI + 플러그인 비노출(후속 플러그인화 시 헤더 주입) + 도메인 허용목록 |
| API 변경 | 서비스별 어댑터 분리(호스트 내장이어도 모듈 경계 유지) |
| B3 회귀 | 화이트리스트는 **이 ADR 근거와 함께만** 확장 — CI 게이트 유지 |
| 심사/레이트 리밋 | 사용자 client_id라 앱 전역 쿼터 위험 없음(1차) |
