## 결론

1. **지연의 95%는 `QueryContextMenu` 한 호출** — 등록된 셸 확장 19개가 순서대로 실행되는 시간이다. 앱 자체 처리(경로·병합·표시)는 50~100 ms.
2. 탐색기가 빠른 이유는 **같은 확장을 오래 떠 있는 프로세스에서 이미 로드·데워 둔 상태**로 쓰기 때문이다. 탐색기도 새 창의 첫 우클릭은 0.8~4.5 s로 느렸다.
3. Nexa의 웜 상태가 탐색기보다 여전히 0.5~1.3 s 느린 것은, 우리 프로세스가 확장 객체를 매번 새로 만들고(특히 .NET 확장 92 ms) OneDrive 경로에서 확장들이 동기화 상태를 질의하기 때문이다.

1. **기동 후 유휴 시 예열**(소): 백그라운드 STA 스레드에서 현재 폴더 파일 하나로 `QueryContextMenu`를 1회 미리 수행 → DLL·CLR 로드가 프로세스에 남아 첫 우클릭 콜드 비용(약 0.7~1.5 s)을 제거.

3. **새로 만들기 병합 지연 로드**(소): 서브메뉴를 펼칠 때 `CLSID_NewMenu`를 초기화(25~59 ms 절감).

### 권장 설계 — 전용 메뉴 스레드 + 선행 구축(A)

1. **전용 STA 스레드 1개**가 숨은 소유자 창을 갖고 메뉴의 전 생애(구축·표시·서브메뉴 포워딩·명령 실행)를 맡는다(프록시 부재 제약을 정면으로 따름). UI 스레드는 메뉴 질의 중에도 멈추지 않는다.
2. **선행 구축**: 단일 선택이 300 ms 머물면 그 항목으로 `QueryContextMenu`까지 끝낸 HMENU를 준비. 진행 중 선택이 바뀌면 결과 폐기(세대 가드), 동시 1건.
3. **우클릭**: 준비된 메뉴가 같은 대상·같은 조건(Shift 확장 동사·클립보드 붙여넣기 가능 여부)이면 즉시 표시 → 예상 **20~30 ms**(현재 0.7~2.1 s). 준비 전이면 준비 완료 즉시 표시(UI는 응답 유지).
4. **결과 반환**: 가로채기 동사(delete·rename·copy·cut)·고유 항목은 UI 스레드로 PostMessage, 셸 동사는 메뉴 스레드에서 `InvokeCommand`(소유자 = 메인 창).
5. 위험: 메뉴 스레드 창의 전경 활성화(AttachThreadInput 필요 여부 실측) · 선택마다 확장이 실행되는 CPU 비용(머무름 300 ms·1건 제한으로 억제) · 선행 구축 후 파일 변경(디렉터리 감시 통지로 폐기).
6. 규모 = 대(3~4 슬라이스): ① 메뉴 스레드로 이전(동작 동일) ② 선행 구축 ③ 무효화 규칙 ④ ui-qa 회귀(`ctxmenu-timing.ps1` 목표 ≤ 50 ms).
